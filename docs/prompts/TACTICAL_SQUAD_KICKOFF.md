# Kickoff prompt — Tactical Squad Plan (multi-agent orchestration)

Paste the block below into a Claude Code session opened at the repo root with multi-agent orchestration enabled.

---

You are the orchestrator for the **Tactical Squad Plan** in the Rust Legions repository.

## Repository

- GitHub: `https://github.com/blae-code/rust-legions` (`blae-code/rust-legions`). Integration branch: `main`.
- If not already inside the repo, clone it: `git clone https://github.com/blae-code/rust-legions.git && cd rust-legions && npm install`. Then `git fetch origin && git checkout main && git pull --ff-only`.
- The repo is two-way synced with the Base44 Builder: **everything merged to `main` lands in the live app's builder on the next sync.** Never merge a red lane to `main`. Lane branches (`feat/tactical-<lane>`) are pushed to origin and opened as PRs against `main`; the orchestrator merges them in the §5 order.
- Backend functions run only on Base44 — pushing `base44/**` compiles nothing locally, which is why platform-owned files are excluded from lanes.

Read, in this order, before doing anything else: `CLAUDE.md`, `AGENTS.md`, `docs/VISION.md`, `docs/TACTICAL_SQUAD_PLAN.md`. The plan document is the contract — lanes, file ownership, payload shapes, phase order, and drift guards are all defined there and are not negotiable inside a lane. If a lane discovers a contract must change, it edits `docs/TACTICAL_SQUAD_PLAN.md` §4 first and states the change in its PR body.

## Your job

1. Spawn one sub-agent per worktree lane using `scripts/agent-worktree.sh tactical-<lane>` (branch `feat/tactical-<lane>`, pushed to `origin`, PR against `main`). **Systems lanes:** **A** rules core, **B** field generator, **C** engine, **D** squad builder UI, **E** arena UI. **Content lanes:** **F** units/specialists/upgrades, **G** research/armory/decrees, **H** factions/houses/lore, **I** the Arms Catalogue (granular weapons + the universal damage model), **J** the Motor Pool (granular mechanized kit). Give each agent only: the four docs above, its owned file list from §3, `test/helpers/*`, and the contracts in §4. Content lanes additionally get `docs/LORE.md`, `docs/FACTION_ROSTER.md`, `docs/GEAR_LIBRARY.md`, `docs/TECH_DESIGN.md`, `docs/HERALD_VOICES.md`, `docs/GAME_RULES.md` and the current `src/lib/imageLibrary.js` (for the `P(...)` placeholder pattern and existing keys). Do not give lanes each other's files.
2. Enforce the **phase order** in §5. Systems track: A and B in parallel; C after A/B merge with `npm test` green; D and E in parallel after C, coding against §4 shapes and the fixture `test/fixtures/tactical-state.json` (Lane C produces it from its scripted-battle test). Content track runs concurrently: F, G and I in parallel from the start; J after I merges (J's hardpoints and facings reference I's tables); H after F/G/I/J merge (H references their keys). F, I and J must merge before D starts. Lane A imports `resolveHit` from I's `arms.ts` — I's damage-model tables must merge before A finalises combat resolution.
2b. **Content lanes author data and prose only — never visuals.** Everything that needs art is registered as a placeholder plate in `src/lib/imageLibrary.js` (`P(key, category, title, desc, prompt, aspect)`, `url` null, prompt without the house style). No image files, no SVGs, no `PLATE_URLS`, no `UnitSprite.jsx` edits — the Base44 session generates all art from those placeholders. Content lanes go **deep and wide**: meet or exceed every minimum in §3 F–J (16+ squad types, 10 specialists, 10 upgrade kits, ≥20 techs with capstones, 20+ armory items incl. relic projects, 13 house presets with unique rosters, herald voices for all, 40+ codex entries, 10 settlement hooks). Every effect is numeric via the §4 `effects[]` vocabulary; every existing key is preserved byte-for-byte; every new rules section in `GAME_RULES.md` is marked `[PROPOSED — awaiting platform wiring]`.
2c. **Lane I goes granular — Enlisted meets Borderlands.** "Rifles" is a class, not a weapon. Author ≥8 fictional manufacturers (each tied to a Great House or settlement culture, with a consistent stat signature, name-stems and native/licensed/captured access), ≥10 calibres with logistics classes, ≥40 hand-named weapon patterns in in-world nomenclature (pattern year + maker + mark), 5 quality grades, ≥25 slot-based modifications each with a numeric tradeoff, ≥20 named quirks each with a machine-evaluable condition, a seeded pure `rollWeapon()` (`mulberry32`, never `Math.random`) and a `deriveLoadout()` roll-up so the engine only ever sees squad-level numbers. Every maker, pattern and mod kit gets a placeholder plate; every maker and calibre gets a Codex entry.
2d. **Lane I also owns the universal damage model.** Every weapon of every scale declares `armorPen`, a `damageType` (kinetic / explosive / shaped / incendiary / fragmentation / concussive / chemical) and an `aoe` (radius + falloff, or null). Every stand declares an `ArmourClass` (none / soft / light / medium / heavy / superheavy / fortified) with a numeric `armourValue`; vehicles declare one per facing. Author `PEN_TABLE` (armorPen − armourValue → multiplier, with a genuine 0 row so rifles cannot hurt heavy crawlers — they may only suppress), `TYPE_MATRIX` (damage type vs armour class: shaped beats plate but wastes on soft; incendiary ignores plate but not sealed hulls; fragmentation shreds soft and is spent on light+; concussive stuns crews) and `resolveHit()`. AoE rolls against each victim's own armour class with per-hex falloff. This is the only place armour math may live.
2e. **Lane J goes granular for mechanized units.** A "crawler" is a chassis class, not a vehicle. Author ≥18 chassis patterns (scouts, line, heavy, land-forts, half-tracks, armoured cars, SP guns, tractor guns, gunboats, fighters, bombers) with tonnage, crew, hardpoints and per-facing base armour; ≥8 powerplants; ≥10 armour packages; ≥6 suspension/drive types with terrain modifiers; ≥8 turrets/mounts; ≥25 vehicle mods each with a numeric tradeoff; ≥15 vehicle quirks with machine-evaluable conditions; motor-works appended to I's `MANUFACTURERS` (keys `mw_*`); hardpoint weapons drawn only from I's `WEAPON_PATTERNS`; a seeded pure `rollVehicle()`; a `deriveMechanized()` roll-up yielding squad-shaped values plus `facings` so the engine treats a vehicle as a stand with facings, never as a bag of parts. Every chassis, powerplant and refit kit gets a placeholder plate; every motor-works and chassis class gets a Codex entry.
3. Every lane PR must pass the §6 drift guards: `npm test`, `npm run lint`, `.claude/hooks/rules-guard.sh`; mirror test green; exported API of `base44/shared/tacticalEngine.ts` unchanged; no `package.json` changes; no hex colors or non-literal Tailwind classes; `@/` imports only; Ministry-voice copy; components ≤ ~60 lines, one per file.
4. Merge in the executed wave order recorded in `docs/prompts/ORCHESTRATION_LOG.md` (I/B/G → A/J → C/F → H → hand-off → D/E). Re-run `npm test` after each merge. Stop on the first red and route it back to the owning lane — never fix another lane's file yourself.
5. **Do not touch platform-owned files:** `base44/functions/gameEngine/entry.ts`, anything under `base44/entities/`, `Patch` records, or anything requiring a live backend deploy or `test_backend_function`. Collect every such need into `docs/prompts/PLATFORM_HANDOFF.md` as a checklist (exact function bodies to insert, exact entity schema JSON, exact action names) so the Base44 chat session can apply them after Phase 2.

## Guarding against drift

- Before spawning, write `docs/prompts/LANE_BRIEFS/<lane>.md` for each lane: its goal, owned files, the §4 shapes it consumes/produces, its acceptance criteria copied verbatim from §3, and the drift guards. Sub-agents work only from their brief plus the four docs.
- Every 2 PRs, diff `base44/shared/tactical.ts` against `src/lib/tactical/data.js` and confirm the mirror test still covers every exported table. If a lane added a table without a mirror, reject.
- Any number that appears in UI copy must be imported from `src/lib/tactical/data.js`. Grep for retyped constants in D/E PRs.
- Keep a running `docs/prompts/ORCHESTRATION_LOG.md`: lane, PR, tests added, contract sections touched, merge timestamp, and any §4 amendments.
- For Lane I PRs also check: no `Math.random`; a 10 000-roll distribution test exists; every quirk has a `condition`; every mod has a non-empty `tradeoff`; `deriveLoadout` output keys ⊆ §4 `SquadType` value keys; the Points Audit prices every pattern at `issue` grade; every pattern declares `armorPen`, `damageType` and `aoe`; `PEN_TABLE` contains a `mult: 0` row; a test proves an issue `rifle`-class weapon does 0 effective damage to a `heavy` target while an `anti_armor`-class weapon does not.
- For Lane J PRs also check: no `Math.random`; distribution test present; every hardpoint weapon key exists in `WEAPON_PATTERNS`; every chassis declares all four facings; every vehicle mod has a non-empty `tradeoff`; `deriveMechanized` output keys ⊆ §4 `SquadType` value keys ∪ `{facings}`; no armour arithmetic outside `arms.ts` (grep `motorPool.ts` for `armourValue` math and reject).
- For Lane A/C PRs also check: penetration is resolved only via `resolveHit` imported from `arms.ts`; hits on vehicles select a facing.
- For content PRs, additionally check: no renamed/removed catalog keys; each new squad/tech/decree/house has its placeholder plate; each `pts` value appears in the Points Audit; lore names don't collide with `docs/LORE.md`; no PII; placeholder prompts don't repeat the house style. Maintain `docs/prompts/ART_MANIFEST.md` — every placeholder key added (key, category, aspect, one-line subject) so the Base44 session can batch-generate them.

## Deliverable back to the human

When A/B/C and F/G/H/I/J are merged (end of Phase 2 + C2): stop, post `PLATFORM_HANDOFF.md` (engine wiring, entity changes, catalog imports, effect application, locks, herald voices) and `ART_MANIFEST.md` (every placeholder plate to generate), and wait — Phase 3 and C3 are applied in the Base44 session. Resume D/E only after being told Phase 3 is live. Finish by summarizing: files added per lane, content counts per catalog, tests added, contract amendments, and open questions — no code in the summary.
